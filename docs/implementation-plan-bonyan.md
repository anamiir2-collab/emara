# خطة تنفيذ بُنيان — مراجعة وتطوير مستودع Emara

> الحالة: وثيقة تخطيط أولية فقط. لم تُنفّذ بعد تغييرات في سلوك التطبيق أو قاعدة البيانات.
> المستودع الحالي: https://github.com/anamiir2-collab/emara
> الفرع: bonyan/foundation-plan

## 1. الهدف والقرارات

تحويل التطبيق الحالي إلى **بُنيان** لإدارة العمارات السكنية في مصر، مع تطبيق Android وiOS، وواجهة عربية RTL، ومحاسبة دقيقة، وحسابات منفصلة للمالك والمدير والمحاسب والساكن، ومساعد صوتي لا يعتمد أي عملية مالية دون مراجعة المستخدم وتأكيده.

القرارات المبدئية:
- عدم حذف الوظائف الحالية قبل جردها واختبارها وتحديد بديل مكافئ.
- إعادة استخدام الحسابات المالية النقية والواجهة حيثما تثبت سلامتها.
- إبقاء التخزين المحلي الحالي كأداة استيراد/تصدير أو وضع محلي محدود، وليس مصدر الحقيقة للبيانات المشتركة بين المستخدمين.
- عدم إرسال أي أمر صوتي مباشرة إلى دفتر الأستاذ دون تحقق الخادم ومراجعة المستخدم.
- العمل في فرع منفصل وفتح Pull Request بدل التعديل المباشر على main.

## 2. نتائج مراجعة الملفات الأولية

تمت قراءة الملفات التالية عبر GitHub: index.html، manifest.webmanifest، service-worker.js، js/config.js، js/database.js، js/migrations.js، js/calculations.js، js/ledger.js، js/backup.js، js/app.js، js/modules/resident-portal.js، js/modules/settings.js، tests/financial.test.mjs، css/base.css.

الملاحظات:
- التطبيق الحالي PWA يعمل بقاعدة IndexedDB محلية؛ لا يوجد خادم مركزي يزامن البيانات بين أجهزة السكان.
- بوابة الساكن موصوفة داخل الكود بأنها عرض محلي غير آمن، ولا يجوز تقديمها على أنها مصادقة متعددة المستخدمين.
- الحسابات مكتوبة بوحدة القرش الصحيحة، وهناك اختبارات Node للحسابات المالية.
- يوجد دفتر عمليات ونسخ احتياطي واستعادة وسجل تدقيق محلي؛ يجب فحص كل مسار وقيود قاعدة البيانات قبل اعتباره جاهزًا للإنتاج.
- الهوية الحالية أخضر غابي وعاجي واتجاه RTL ويمكن تطويرها إلى بُنيان دون تغيير جذري.
- ملف service-worker يخزن ملفات التطبيق محليًا؛ يجب أن لا يخزن استجابات API الخاصة أو بيانات المستخدم الحساسة في Cache API.

هذه مراجعة أولية وليست تدقيقًا شاملًا لكل الملفات، ولم تُشغّل الاختبارات بعد في بيئة تنفيذية.

## 3. مقارنة خيارات الخادم

### الخيار A: Supabase (الاختيار المبدئي الموصى به)
- PostgreSQL مُدار، Auth، سياسات Row Level Security، تخزين، ومهام خادمية/Edge Functions.
- يقلل عبء إدارة الخادم والتحديثات والنسخ الاحتياطي مقارنة بإدارة خادم كامل.
- مناسب لربط كل سجل بمعرّف المؤسسة/العمارة وفرض صلاحيات الوصول في قاعدة البيانات.
- يلزم ضبط RLS واختباره بعناية؛ إعداد خاطئ قد يكشف بيانات. لا يوضع service-role key أو أي مفتاح سري داخل تطبيق الهاتف.
- تُستخدم Edge Functions أو خدمة خلفية موثوقة لعمليات الذكاء الاصطناعي التي تتطلب مفاتيح سرية، مع حدود استخدام وتسجيل آمن.
- يجب التحقق من الأسعار والحدود ومكان استضافة البيانات قبل اعتماد الخطة التجارية.

### الخيار B: خادم مخصص Node.js + PostgreSQL
- تحكم كامل في منطق العمل، المعاملات، والتكاملات.
- يتطلب مسؤولية إضافية عن الاستضافة والتحديثات والمراقبة والأمان والنسخ الاحتياطي والتعافي.
- مناسب إذا ظهرت لاحقًا متطلبات تشغيل أو تكاملات لا تناسب الخدمات المُدارة.

### الخيار C: استمرار IndexedDB فقط
- الأقل تكلفة في البداية ويعمل محليًا، لكنه لا يوفر مزامنة حقيقية أو حسابات آمنة مشتركة بين الأجهزة.
- غير مناسب كخيار إنتاجي لتطبيق مالك/مدير/ساكن متعدد المستخدمين.

**القرار المبدئي:** بدء نموذج أولي بـ Supabase لتقليل تكلفة التشغيل والإدارة، مع إبقاء طبقة الخدمات في تطبيق الواجهة قابلة للاستبدال. يُعاد تقييم القرار بعد اختبار RLS، تجربة الصوت، التسعير، ومتطلبات إقامة البيانات. لا يعتبر هذا القرار نهائيًا قبل مراجعة الأسعار والسياسات الحالية.

## 4. نطاق النسخة الأولى (MVP)

### الإدارة
- تسجيل الدخول وإدارة المؤسسة/العمارة.
- المباني والشقق والسكان والعقود والالتزامات.
- التحصيلات الجزئية والكاملة وتخصيص الدفعات.
- المصروفات المدفوعة وغير المدفوعة.
- الإيصالات، التقارير، التصدير، وسجل التدقيق.
- استيراد البيانات القديمة مع معاينة ونسخة احتياطية قبل الترحيل.

### الساكن
- حساب فردي موثّق مرتبط بالشقة/العلاقة السكنية.
- عرض مستحقاته ودفعاته وبيانات شقته فقط.
- عرض المصروفات المشتركة والتقارير التي تسمح بها سياسة العمارة.
- تقديم طلب صيانة ومتابعة حالته.
- إشعارات وتذكيرات قابلة للتحكم.

### المساعد الصوتي
- تسجيل صوت بعد إذن واضح من المستخدم.
- تحويل الكلام إلى نص وفهم اللهجة المصرية.
- استخراج نوع العملية والمبلغ والساكن والشقة والتاريخ وطريقة الدفع.
- عرض مسودة قابلة للتعديل؛ لا كتابة في السجل المالي قبل ضغط «تأكيد».
- عند وجود التباس أو أكثر من ساكن متشابه الاسم، يتوقف ويسأل.
- حفظ سجل تدقيق لعملية التأكيد؛ لا يحتفظ بالصوت الخام افتراضيًا.
- عدم وضع مفاتيح مزودي الذكاء الاصطناعي في تطبيق الهاتف.

## 5. قواعد الحسابات والأمان

- تخزين الأموال كأعداد صحيحة بوحدة القرش؛ منع NaN والقيم السالبة أو غير المنطقية حيث لا يسمح بها نوع العملية.
- جميع عمليات الدفعات والإيصالات والتخصيص وسجل التدقيق تتم بمعاملة قاعدة بيانات واحدة.
- مفتاح idempotency فريد لكل عملية مؤكدة لمنع التكرار عند إعادة المحاولة أو انقطاع الشبكة.
- لا يعتمد منع التكرار على بصمة محتوى فقط؛ قد يدفع المستخدم المبلغ نفسه مرتين فعلًا. يجب توفير مفتاح طلب فريد مع تحذير مناسب عن التشابه.
- لا تُحذف العمليات المالية المعتمدة؛ التصحيح من خلال عملية عكس موثقة وصلاحية مناسبة.
- الرصيد النقدي = الرصيد الافتتاحي + التحصيلات الفعلية − المصروفات المدفوعة فقط.
- عزل كل مؤسسة/عمارة على مستوى قاعدة البيانات، والتحقق من الصلاحيات على الخادم لا في الواجهة فقط.
- اختبارات RLS سلبية وإيجابية لكل دور، واختبارات عدم الوصول بين عمارتين.
- استخدام HTTPS، أسرار خادمية، حدود للمعدل، تنقيح السجلات من البيانات الحساسة، وخطة نسخ احتياطي واستعادة مجربة.
- لا تخزن Cache API أو service worker استجابات API الخاصة أو التسجيلات أو التقارير التي تحتوي بيانات شخصية.

## 7. خطة التعديل حسب الملفات

### مرحلة 0 — تدقيق قبل التغيير
- تشغيل `node --test tests/` في بيئة تطوير.
- فحص جميع ملفات `js/modules/` والاختبارات وتبعيات الواجهة.
- توثيق سلوك كل شاشة، والحقول المستخدمة، وتنسيق التواريخ والمبالغ.
- مراجعة العمليات المالية وحدودها واختبارات فشل المعاملات.
- لا حذف ولا إعادة تسمية واسعة قبل اكتمال الجرد.

### مرحلة 1 — هوية بُنيان
- `index.html`: اسم التطبيق، العنوان، الوصف، وبيانات PWA.
- `manifest.webmanifest`: الاسم والاسم المختصر والأوصاف.
- `js/config.js`: اسم التطبيق وإعداداته دون تغيير مفاتيح البيانات القديمة قبل خطة ترحيل.
- `css/base.css` وبقية CSS: الحفاظ على لوحة الأخضر والعاجي وتطوير تفاصيل الهوية.
- `service-worker.js`: إصدار cache جديد وسياسة تمنع تخزين البيانات الحساسة.

### مرحلة 2 — طبقة الخدمات والخادم
- إضافة طبقة خدمات مستقلة بدل استدعاء IndexedDB مباشرة من كل شاشة.
- إبقاء محول IndexedDB للبيانات المحلية/الاستيراد، وإضافة محول API للخادم.
- إعداد مخططات قاعدة البيانات والترحيلات وسياسات الوصول.
- عدم توصيل واجهة الإنتاج بالخادم قبل نجاح اختبارات الصلاحيات.

### مرحلة 3 — دفتر الأستاذ
- مراجعة `js/calculations.js` و`js/ledger.js`، ونقل القواعد المعتمدة إلى منطق خادمي موثوق.
- إنشاء اختبارات للتخصيص الجزئي، والتزامن، وعكس الدفعات، وتكرار الطلبات، والأرقام الكبيرة.
- الاحتفاظ باختبارات الحسابات النقية وإضافة اختبارات تكامل للخادم.
- ترحيل البيانات القديمة عبر معاينة ومطابقة إجماليات قبل اعتمادها.

### مرحلة 4 — الحسابات والصلاحيات
- إنشاء تسجيل الدخول وربط الأعضاء بالمؤسسات والعمارات.
- استبدال اختيار الساكن المحلي في `js/modules/resident-portal.js` ببوابة مصادق عليها.
- مراجعة كل وحدة بحيث تجلب البيانات من طبقة الخدمات وتتعامل مع حالات انقطاع الشبكة وانتهاء الجلسة.

### مرحلة 5 — الصوت
- إضافة وحدة مستقلة للمساعد الصوتي وواجهة API خادمية.
- حالات صريحة: recording → transcription → draft → validated → confirmed/rejected.
- لا تنفذ الأداة أي كتابة مالية من مرحلة draft.
- تأكيد المستخدم مطلوب لكل تحصيل أو مصروف أو عكس أو تعديل مالي.
- إضافة اختبارات لأوامر عربية، أسماء متشابهة، مبالغ ملتبسة، رفض الإذن، وانقطاع الشبكة.

### مرحلة 6 — إشعارات وتطبيقات الهاتف
- إضافة خدمة إشعارات وموافقة المستخدم وإدارة رموز الأجهزة.
- إضافة Capacitor وإعداد Android وiOS، ثم اختبار الإذن للميكروفون والإشعارات والروابط العميقة.
- إنشاء GitHub Actions للفحص والاختبار والبناء، مع الأسرار خارج المستودع.

## 8. معايير القبول

- جميع اختبارات الحسابات القديمة والجديدة ناجحة.
- لا يمكن لساكن قراءة بيانات ساكن آخر أو لأي عضو الوصول إلى عمارة غير مخول بها.
- لا يتم إنشاء تحصيل أو مصروف من الصوت قبل التأكيد الصريح.
- تكرار إرسال الطلب نفسه لا ينشئ إيصالًا أو دفعة ثانية.
- إجماليات الترحيل من النسخة المحلية تطابق المصدر قبل الاعتماد.
- النسخ الاحتياطي والاستعادة مختبران، ولا تتضمن النسخ ملفات أسرار.
- اختبارات الواجهة على Android وiOS تشمل حالات الاتصال الضعيف ورفض الأذونات.
- وثائق الخصوصية توضح معالجة الصوت والبيانات ومزودي الخدمات وفترات الاحتفاظ.

## 9. ما لم يُنفذ بعد

هذه الوثيقة لا تعني أن قاعدة بيانات أو مصادقة أو صوت أو إشعارات خادمية قد أُنشئت. الفرع الحالي يحتوي على وثيقة الخطة فقط. الخطوة التالية هي تشغيل الاختبارات ومراجعة الملفات المالية كاملة، ثم اعتماد مخطط قاعدة البيانات وسياسات الصلاحيات قبل تنفيذ أي نقل بيانات أو تغيير في السلوك.
